Current branch explanation

Person resolution becomes conservative, and duplicate people move into a review queue.

This branch changes Memento's identity pipeline from "merge when the evidence seems good enough" to "merge only when mailbox rules prove equivalence, then ask a human about everything weaker." It adds a persisted suggestion queue, a UI for reviewing it, API endpoints for accepting or rejecting pairs, and a repair command for data created by older resolver behavior.

Background

The system in one paragraph

Memento reads a local msgvault archive and writes derived product tables whose names begin with memento_. The People dimension starts with raw email participants, clusters email addresses into canonical people, classifies which people are meaningful contacts, builds rollups for the UI, and then lets agents enrich selected people with source-attributed notes and narrative sections.

Why identity resolution is dangerous

Email identities are deceptively messy. One human can use many addresses. One display name can belong to many humans. Forwarders and product notifications often attach a person's name to an automated sender. A fuzzy spelling match can be right in a small address book and wrong in a large archive.

Before this branch, the resolver could automatically combine participants using non-mailbox evidence: exact display-name equality, forwarder-unwrapped names, and optionally fuzzy name similarity. That was convenient, but it created a data safety problem. A wrong automatic merge does not merely affect a label. It can mix timelines, notes, facets, project memberships, and generated relationship narratives.

Important safety boundary: a false positive person merge is worse than a missed duplicate. A missed duplicate creates review work. A false positive corrupts the meaning of a person page and can contaminate later generated text.

Person vs People

The codebase uses person and people for related but different layers.

person: identity primitive

This is the backend identity model: canonical rows in memento_person, aliases in memento_person_email, and merge/split/resolve behavior in backend/internal/person.

people: product surface

This is the People dimension users see: candidate classification, UI rollups, directory rows, and People page reports in backend/internal/people and memento_people_report.

Intuition

The central idea is to separate two questions that used to blur together:

Question 1: Are these the same mailbox?

This can be answered deterministically for a small set of provider rules. If yes, Memento may link automatically.

Question 2: Are these the same human?

This often needs judgment. Memento can rank likely duplicates, but the user confirms the merge.

The new mental model

The review queue is not a temporary report. It is a product state machine. A pending row can become accepted or rejected. If rejected, rerunning the resolver should not bring it back. If accepted, the merge happens transactionally and any stale pending suggestions involving the absorbed person are also resolved.

Code Walkthrough

1. The resolver stops auto-merging on names

backend/internal/person/matcher.go is the heart of the behavior change. The old normalized-name pass, forwarder re-tagging pass, and optional fuzzy merge pass are removed as automatic cluster merges. The resolver now forms clusters by normalized email only, then calls collectResolveSuggestions to emit advisory duplicate signals.

func Resolve(ctx context.Context, reader *msgvault.Reader, locked map[string]bool, opts ResolveOptions) (ResolveReport, []cluster, error) {
    // Build cluster members, skipping locked emails.
    // Pass 1: group by normalizeEmail(email).
    // Multi-member groups are plus_tag links.

    report.Suggestions = collectResolveSuggestions(members, clusters, opts)

    // Materialize clusters. Singletons become singleton links.
    return report, out, nil
}

ResolveOptions also changes meaning. The old IncludeFuzzy switch disappears from the data model. Thresholds such as Jaro-Winkler and Jaccard still exist, but they only affect whether a suggestion is emitted.

Key design move: the resolver still computes weak identity signals, but those signals no longer decide database identity on their own.

2. Email normalization becomes provider-specific

backend/internal/person/normalize.go defines the deterministic gate. It lowercases every address, strips plus-tags only for known plus-capable providers, strips dots only for Gmail and Googlemail, and refuses to strip plus-tags for system-looking local parts.

var providerEmailNormalization = map[string]emailNormalizationRules{
    "gmail.com":      {stripPlusTag: true, stripDots: true},
    "googlemail.com": {stripPlusTag: true, stripDots: true},
    "hey.com":        {stripPlusTag: true},
    "fastmail.com":   {stripPlusTag: true},
    "pm.me":          {stripPlusTag: true},
    "proton.me":      {stripPlusTag: true},
    "protonmail.com": {stripPlusTag: true},
}

The tests make the policy concrete: Gmail dot variants merge; Fastmail dot variants do not. Same-name cross-domain people do not merge, but do create a suggestion.

3. Suggestions become durable rows

The new migration creates memento_merge_suggestion. Each row stores an ordered pair of people, evidence sources, scores, stale-score state, and a review status.

CREATE TABLE IF NOT EXISTS memento_merge_suggestion (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  person_a_id INTEGER NOT NULL,
  person_b_id INTEGER NOT NULL,
  sources TEXT NOT NULL DEFAULT '[]',
  name_similarity REAL NOT NULL DEFAULT 0,
  token_overlap REAL NOT NULL DEFAULT 0,
  signature_score REAL NOT NULL DEFAULT 0,
  combined_score REAL NOT NULL DEFAULT 0,
  scores_stale INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'pending',
  resolved_at DATETIME,
  CHECK(person_a_id < person_b_id),
  CHECK(status IN ('pending', 'accepted', 'rejected')),
  UNIQUE(person_a_id, person_b_id)
);

This is the persisted review-queue model: the review queue lives in the database, not only in a page render or one command output. A row can be pending, accepted, or rejected. The table has two important invariants. First, the pair is ordered, so (12, 91) and (91, 12) cannot become separate suggestions. Second, only pending rows are updated on reruns. Accepted and rejected decisions are historical product state, not cache entries.

4. Persistence returns a cluster-to-person map

PersistClustersWithMapping extends the existing stable-ID persistence contract. It still reuses existing person IDs when possible, prefers locked mappings, sweeps stale unlocked emails, and deletes orphaned people. It now also returns a map from run-local cluster IDs to persisted person IDs. That map lets resolver suggestions, which are emitted in terms of temporary cluster IDs, become durable person-pair rows.

5. Graph suggestions join the same queue

backend/internal/person/merge.go already had social-graph candidate scoring. This branch routes those candidates into the persisted queue with source graph. The refresh and onboarding flows now call GenerateAndPersistGraphSuggestions after building the social graph.

Before this branch, graph-backed duplicate candidates could be computed and shown, including in the older staged merge-review workflow. The new part is not the existence of graph evidence. The new part is that graph evidence feeds the same durable queue as name, forwarder, fuzzy, and token evidence.

This is why the UI can sort by four schemes:

  • Best match: combined score.
  • Similar spelling: name similarity.
  • Shared name words: token overlap.
  • Mutual contacts: graph signature score.

6. The server exposes a review API

backend/internal/server/routes.go registers two new public endpoints:

GET  /api/people/merge-suggestions?limit=50&sort=combined
POST /api/people/merge-decision

// request body
{"id":"123","decision":"accept"}
{"id":"123","decision":"reject"}

The GET route loads pending suggestions, then loads a compact profile for each person. If a row points at a dismissed or missing person, the route marks it rejected and skips it, avoiding ghost rows in the review queue. The POST route either marks a row rejected or accepts it by choosing a keep/merge direction and calling MergePersons.

7. Accepting a suggestion is transactional

MergePersons transfers the absorbed person's data into the surviving person in one transaction: email aliases, facets, narratives, notes, and project memberships. It marks transferred emails as locked manual_merge, because a user confirmed the identity. It then accepts the pair's pending suggestion and rejects other pending rows involving the absorbed person.

Terminology note: earlier drafts of this branch used signature_merge for accepted review merges. That was misleading because an accepted review merge is a manual user decision, even if the original suggestion came from name match, forwarder evidence, fuzzy spelling, token overlap, or graph signature. The stored source is now manual_merge, meaning "confirmed by the user via duplicate review and protected from future resolver changes." 
// During MergePersons:
// 1. Move emails to the survivor.
// 2. Mark moved emails locked with link_source = manual_merge.
// 3. Move facets, narratives, notes, and project memberships.
// 4. Mark the accepted suggestion accepted.
// 5. Reject stale suggestions involving the absorbed person.
// 6. Delete the absorbed person.

8. The UI becomes a real review surface

src/app/people/merge-review/page.tsx no longer computes a one-off candidate list. It fetches persisted suggestions, displays the evidence, recommends a keep direction, and lets the user accept or reject each pair individually.

The route path is unchanged: /people/merge-review/ still exists. What changes is the implementation behind the route. The older UI had staged selections, a "Stage selected" action, and a batch "Commit staged" action. This branch replaces that under the same URL with a persisted-queue UI backed by GET /api/people/merge-suggestions and POST /api/people/merge-decision.

9. Legacy over-merges get an explicit repair command

backend/internal/person/repair.go adds person-repair-nondeterministic. It scans existing memento_person_email rows and looks for unlocked links whose source was one of the old unsafe resolver signals: exact_name, forwarder_unwrap, jaro_winkler, or jaccard.

The command plans splits by normalized email group. For each person, it keeps the safest group: the one containing the primary email if present, otherwise a locked/manual/manual-merge anchor, otherwise the largest and oldest deterministic group. Unsafe non-equivalent groups are split into new locked/manual people when --apply is used.

./memento person-repair-nondeterministic --dry-run
./memento person-repair-nondeterministic --apply

This is intentionally not automatic. Repairing historical identity data is a data migration with user-visible consequences, so the branch makes it an operator action with dry-run output.

10. Documentation and decision log are updated

The README, deterministic extraction guide, current-state spec, and DECISIONS.md now describe the conservative identity policy, the merge review queue, the new API endpoints, the updated CLI commands, and the repair workflow.

How The Changes Take Effect

Building and running this branch changes the application code, but it does not automatically rewrite your existing local Memento tables just because you open the People page.

What changes immediately after build

The route /people/merge-review/ serves the new page implementation. It asks the backend for persisted suggestions instead of showing the old staged batch workflow.

What does not happen automatically

Already resolved people are not split or removed by page load. Existing bad historical merges remain until you explicitly run the repair flow.

The command ./memento person-resolve --persist is not new. What changes in this branch is its behavior: automatic persistence is now limited to deterministic mailbox-equivalent clusters, and weaker duplicate evidence is persisted as review suggestions.

To populate the new queue after switching to this branch, the typical sequence is:

./memento migrate
./memento person-resolve --persist
./memento refresh --people

If you want graph-backed suggestions, the social graph also needs to be current. The setup and people refresh flows in this branch call graph suggestion persistence after building the graph.

For old over-merges created by previous resolver behavior, use dry-run first:

./memento person-repair-nondeterministic --dry-run
./memento person-repair-nondeterministic --apply
Practical consequence: if your current old merge-review page shows many live-computed suggestions, those exact rows are not guaranteed to appear after only building this branch. The new page reads memento_merge_suggestion. Until that table is migrated and populated, the new page may show fewer suggestions or none.

Edge Cases

Rejected pairs do not resurface

UpsertMergeSuggestion inserts or updates pending rows, but if the existing row is accepted or rejected, it leaves it alone.

Missing people do not block the UI

The suggestion GET route marks stale rows rejected if either side no longer has an active person profile.

Graph scores can arrive later

Name-based resolver suggestions may have scores_stale. Later graph evidence can update the same pending row and clear that flag.

Manual decisions survive resolver reruns

Locked email mappings are skipped by the resolver, and user-confirmed merge emails are locked as manual_merge.

Repair preserves anchors

Legacy repair does not split locked, manual, signature-merge, or deterministic normalized-email groups.

The old fuzzy flag becomes harmless

person-resolve --fuzzy is now a deprecated no-op for automatic linking. Threshold flags only tune advisory suggestions.
